## 0. 一句话结论

六阶段计划把「模拟器」修成了**一台不会崩、账能对上、界面能读**的机器；v3 指出这台机器**缺的是玩家与世界的对抗**。

v4 的目标：**在已经确定的世界之上，把「时间、承诺、对手、代价、传承」五件事做成玩家每月都要回答的问题**——同时不破坏单文件、确定性、4 秒、存档迁移这些硬约束。

## 2. 计划合并方式

### 2.1 合并原则

1. **v3 是体验方向的权威**：它回答「为什么现在的游戏不好玩」，优先级高于任何局部优化。
2. **六阶段是工程质量的权威**：它回答「哪些东西会崩、会算错、会读不出来」，任何新系统都必须先满足这些护栏。
3. **已交付的能力不重做**，只补差量（见 §1.4）。
4. **每条改动必须有可执行的验收**（命令或测试名），没有验收的条目不进排期。
5. **一次只动一条主干**：时间预算、议程、经济闭合三条主干不允许并行开工（都会改 `dispatch` 与月度结算）。

## 3. 统一目标（可验收的三层）

### 3.1 体验目标（定性命中率）

三句话必须成立，任一条不成立则方向失败：

1. 新玩家在 20 分钟内能说出**「我在等什么、我怕什么」**（带人名与天数）。
2. 每个 30 天的月份里，至少有**一次取舍**（做了 A 就做不了 B），且**没有标准答案**。
3. 角色死亡/交班时，玩家能**复述这一生做了什么**，并看到下一代的起点。

### 3.2 系统目标（不变量）

- 单一写入口 `GameEngine.dispatch`；随机唯一来源 `Random`；时间唯一入口 `GameClock`；core 不依赖 UI；遍历按稳定 ID。
- 单文件 `release/index.html`、零外链、`file://` 可跑、≤ 1.5 MiB。
- 100 年模拟 < 4.0 s（CPU 时间口径，见 `tests/simulation.test.ts`）。
- 存档逐级迁移，每级有往返测试；`SCHEMA_VERSION` 与 `SAVE_FORMAT_VERSION` 同步。
- `tsc` / `eslint` / `prettier` / `vitest` 全绿是提交门槛，不是目标。

**依赖**：W3（处境板数据）+ W1（月报）。**风险**：UI 大改会打碎现有 jsdom 测试（`app-modal-pause`、`stage6-ui`）——先加新布局的查询钩子，再改结构，最后删旧断言。

## 6. 排期（P0–P8）与依赖图

```
P0  W0 止血包 + 测量基建           ── 无依赖，先做
P1  W1 月末结算 + 月报             ── P0
P2  W2 时间预算                    ── P1   （主干①）
P3  W3 议程 + 计划                 ── P2   （主干②）
P4  W4 对手 + 情报                 ── P3
P5  W5 承诺/信用/失败线            ── P3
P6  W6 阶梯与仕途                  ── P5
P7  W7 关系/人情/声望/王朝         ── P5,P6
P8  W8 内容 2.0 + 终局             ── P3,P7
    W9 经济闭合                    ── P2 之后任意时点，独占主干（不与 P3 并行）
    W10 叙事与史书                 ── P1,P8 持续
    W11 界面 2.0                   ── P3 之后，可与 P4–P7 并行（只改 ui/）
```

**排期原则**

1. P0–P3 是「骨架四连」，期间**不加内容**、**不动经济参数**（否则测量基线失效）。
2. P3 之后允许并行三条线：玩法（P4/P5/P6/P7）、内容（P8）、界面（W11），但**同一文件同一时刻只有一个负责人**（`src/core/GameEngine.ts` 与 `state` schema 是热点）。
3. 每个 P 结束必须：`tsc` → `eslint` → `prettier` → `vitest` → `vite build` → `release` → `measure` 快照 → 文档（`development-plan.md` §8.x + README）→ commit + push。
4. 每个 P 结束用三 seed 100 年 + `measure` 全量对照 §3.3；**只允许两项指标回退**，且必须写明原因。
